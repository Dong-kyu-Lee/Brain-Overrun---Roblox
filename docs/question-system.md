# 문제 시스템 (Phase 3)

> 이 문서는 **코드를 읽기 전에 읽는 문서**다.
> `QuestionBank` / `QuestionService` / `QuestionDisplay` / `Hud` 를 수정하거나,
> 새 문제를 추가할 때 필요한 배경·규약·함정을 담았다.
>
> 맵 좌표계는 [map-builder.md](map-builder.md), 라운드 흐름은 [round-loop.md](round-loop.md) 를
> 먼저 읽을 것. 여기서는 둘 다 안다고 가정한다.

---

## 1. 네 줄 요약

1. **정답은 서버 밖으로 나가지 않는다.** 문제 DB 도, 이미지 ID↔이름 대응표도 서버 전용이고,
   클라이언트가 받는 건 `QuestionService.payloadOf()` 가 만든 것뿐이다.
2. **정답 구역(A/B)은 문제가 아니라 출제 시점에 정해진다.** DB 에는 '정답 보기/오답 보기'만 있다.
3. **매체는 두 축이다.** 문제 본문(`promptKind`)과 선택지(`choiceKind`)가 각각 글자/사진이다.
4. **선택지는 바닥, 본문은 공중 보드, HUD 는 지시문과 타이머.** 화면 중앙은 비운다.

## 2. 데이터 흐름과 보안 경계

```
 서버                                                   │ 클라이언트
 ─────────────────────────────────────────────────────  │ ────────────────────
 ImageAssets     "사진과 그 이름"  rbxassetid ↔ "고양이"  │
       │          ★ 서버 전용 — 이게 새면 정답이 샌다      │
       ▼                                                 │
 QuestionBank    "문제 내용"   make(rng) → 정답/오답     │
       │                       ★ 서버 전용 모듈           │
       ▼                                                 │
 QuestionService "누구를 어디에"  정답을 A/B 중 무작위 배치│
       │                                                 │
       ├── Question { …, answer } ──┐                    │
       │                            │                    │
       │                            ▼                    │
       │                   QuestionDisplay ──┬─ 바닥 SurfaceGui (선택지 2개)
       │                   "월드에 그린다"    └─ 공중 보드 (지시문 + 본문 사진)
       │                                       복제 ─────┼──▶ 눈으로 봄
       │                                                 │
       └── payloadOf() ── QuestionShown ─────────────────┼──▶ Hud (지시문·타이머)
                          ★ answer·promptImage 없음 ★    │
                                                         │
                          GetImageAssets ────────────────┼──▶ ImagePreload
                          ★ 이름표 없는 ID 배열 ★         │   (미리 내려받기)
                                                         │
 RoundService    correctZone = question.answer            │
       └── WallController.rush(correctZone) ─────────────┼──▶ 물리 결과로 판정
```

### 정답이 새는 경로는 다섯뿐이다 — 전부 막혀 있다

| 경로 | 막는 방법 |
|---|---|
| 문제 DB 를 클라이언트가 읽음 | `QuestionBank` 를 `ServerScriptService` 에 둔다. `Shared` 로 옮기지 마라 |
| **이미지 ID↔이름 대응표가 새어 사진을 역변환** | `ImageAssets` 도 `ServerScriptService` 에. 클라이언트에는 `assetIds()` 의 **이름표 없는 평탄한 배열**만 나간다 |
| `QuestionShown` 페이로드에 `answer` 가 섞임 | `payloadOf()` 가 필드를 **하나씩 옮겨 적는다** (§8 참고) |
| 바닥 파트/GUI 에 정답 표시가 남음 | `show()` 는 어트리뷰트·이름·색 어디에도 정답을 기록하지 않는다 |
| 판정 전에 정답을 강조 | `reveal()` 은 `Judge` 단계에서만 호출한다 |

> ### ⚠ 이미지 문제가 만드는 새 누수 경로
> `{ name = "고양이", asset = "rbxassetid://123" }` 이 클라이언트에서 읽히면, 바닥에 뜬
> 사진의 에셋 ID 를 이름으로 되돌려 **문제를 읽지 않고 정답을 찾을 수 있다.**
> 프리로드 목록에서 이름을 뗀 이유가 이것이다 — ID `123` 만으로는 아무것도 알 수 없다.

> ### ⚠ `table.clone` 으로 페이로드를 만들지 마라
> `local p = table.clone(question); p.answer = nil` 은 **지금은** 동작한다.
> 그러나 나중에 `Question` 에 필드가 하나 늘어나는 순간 그게 그대로 클라이언트로 나간다.
> `payloadOf()` 가 필드를 일일이 적는 이유가 이것이다. 귀찮은 쪽이 안전한 쪽이다.

Phase 2 의 `Config.Debug.RevealAnswer`(정답을 전 클라이언트에 `Notify` 로 뿌리던 물건)는
**제거했다.** 대신 `Config.Debug.LogQuestions` 가 **서버 콘솔에만** 출제 내역을 찍는다.
켜 둔 채로 테스트해도 정답이 새지 않는다.

## 3. 문제 DB — `QuestionBank`

### 왜 목록이 아니라 '생성기'인가

기획서 5장의 Type 1 은 사칙연산이다. 정적 목록으로 두면 몇 판 만에 문제가 돌고,
플레이어는 문제를 **읽는 대신 외운다** — 코어 루프가 통째로 죽는다.
그래서 각 항목이 `make(rng)` 로 매번 새 문제를 만든다.

이미지 문제도 같은 규칙을 따른다. 고정된 사진 쌍을 박지 않고, `ImageAssets` 의 세트에서
**매번 두 장을 새로 뽑는다.** 그래서 세트에 항목이 많을수록 문제도 많아진다.

### 매체는 두 축이다 — `promptKind` / `choiceKind`

하나의 `kind` 로 문제 전체를 가르면 아래 네 칸 중 두 칸을 표현할 수 없다.

|  | 선택지 = `text` | 선택지 = `image` |
|---|---|---|
| **본문 = `text`** | `"1+2=?"` → 3 / 4 | `"고양이는?"` → 🐱 / 🌳 |
| **본문 = `image`** | 🐱 → 고양이 / 강아지 | 🐱 → 🐱 / 🌳 |

그래서 `Source` 가 두 축을 따로 들고 다닌다. 본문·선택지가 모두 글자인 흔한 경우는
`textSource(id, difficulty, make)` 헬퍼로 줄여 적는다.

### 이미지 세트 — `ImageAssets`

`{ name = "고양이", asset = "rbxassetid://…" }` 항목을 세트로 묶어 둔 **서버 전용** 모듈이다.
`QuestionBank` 가 세트 하나마다 **서로 반대 방향의 문제 두 종류**를 자동 등록한다.

| Source id | 본문 | 선택지 | 보여주는 것 |
|---|---|---|---|
| `{set}-name` | `image` | `text` | 🐱 + "이 동물은?" → 바닥에 "고양이" / "강아지" |
| `{set}-photo` | `text` | `image` | "고양이는?" → 바닥에 🐱 / 🐶 |

**에셋을 채우면 `QuestionBank` 를 고치지 않아도 문제가 늘어난다.**
항목이 2개 미만인 세트는 보기 두 개를 뽑을 수 없어 아예 등록되지 않는다 —
등록 가능한 세트가 하나도 없으면 이미지 문제가 0종이 되고, 추첨은 조용히 텍스트로 넘어간다 — 에러가 아니라 설계된 폴백이다.

세트를 만들 때 지킬 것:

- **한 세트 안의 항목은 서로 헷갈리지 않아야 한다.** 고양이와 호랑이를 같은 세트에 두면
  바닥에서 눌려 보일 때(§5) 구분이 안 된다. 헷갈리는 쌍은 세트를 나눠라.
- **항목이 많을수록 좋다.** 2개뿐이면 매 라운드 같은 쌍만 나와 중복 회피가 곧바로 막힌다.

### 숫자 범위가 `Config` 에 없는 이유

README 규약 1은 **밸런싱 수치**를 `Config` 에 모으라는 것이다.
`QuestionBank` 안의 `RANGE` / `SPREAD` 는 밸런싱이 아니라 **문제의 본문 그 자체**다 —
"1~9 사이 두 수의 덧셈"은 `"짝수는?"` 이라는 문장과 같은 층위의 콘텐츠다.

경계는 이렇게 긋는다:

| 어디에 | 무엇이 |
|---|---|
| `Config.Question` | **언제 무엇을 뽑는가** — 난이도 커브, 중복 회피 크기, 이미지 출제 확률 |
| `Config.Theme.Screen` / `.Board` / `.Hud` | **어떻게 보이는가** — 색, 폰트, 해상도, 회전 |
| `Config.Map.AnswerBand*` | **어디에 그리는가** — 게임성에 직결되므로 맵 수치다 (§5) |
| `QuestionBank` 내부 | **무엇을 묻는가** — 연산 종류, 숫자 범위, 보기 문구 |

같은 이유로 `Config.Theme` 이 따로 있다(map-builder.md §6). 색을 로직 파일에 박지 않되,
색을 밸런싱 값과 섞지도 않는다.

### 지금 들어있는 것

**텍스트 10종 (난이도 1~5) · 이미지 6종** (3세트 × 2방향).

| 난이도 | id | 예 |
|---|---|---|
| 1 | `compare` | 더 큰 수는? → 73 / 41 |
| 1 | `add-digit` | 4 + 7 = ? |
| 2 | `parity` · `sub-teen` · `add-two-digit` | 짝수는? / 14 - 6 = ? / 37 + 28 = ? |
| 3 | `multiply` · `sub-large` | 7 × 8 = ? / 84 - 37 = ? |
| 4 | `divide` · `multiply-add` | 56 ÷ 7 = ? / 6 × 7 + 3 = ? |
| 5 | `precedence` | 5 + 4 × 3 = ? |

`precedence` 의 오답은 **연산 순서를 무시한 답**`(a+b)×c` 이다. 대충 왼쪽부터 계산한
사람만 정확히 틀리도록 만든 것이며, `c ≥ 2 · a ≥ 1` 이라 정답과 같아지는 경우는 없다.

오답은 전부 `nearMiss()` 로 만든다. 정답에 너무 가까우면 눈으로 못 고르고,
너무 멀면 계산하지 않고 어림짐작으로 맞힌다. 음수 오답은 만들지 않는다 —
하이퍼캐주얼에서 음수는 계산이 아니라 표기 때문에 헷갈린다.

등록된 이미지 세트는 아래 셋이며, 세트마다 `{id}-name` / `{id}-photo` 두 방향이 자동 등록된다.

| 난이도 | 세트 id | 지시문 | 항목 |
|---|---|---|---|
| 1 | `animal` | 이 동물은? | 고양이 · 강아지 · 오리 |
| 1 | `fruit` | 이 과일은? | 사과 · 바나나 |
| 2 | `flag` | 이 국가는? | 브라질 · 인도 |

> ⚠ `fruit` · `flag` 는 항목이 2개뿐이라 매번 같은 쌍이 나온다. 세트당 3~4개가 목표다.

`Config.Question.ImageChance`(0.3)는 **문제 하나가 아니라 '풀'을 고르는 확률**이다
(`QuestionService.poolFor`). `1.0` 으로 두면 해당 난이도에 이미지 문제가 하나라도 있는 한
텍스트 문제가 아예 나오지 않으므로, 이미지만 집중 확인할 때 외에는 올리지 말 것.

## 4. 정답 구역은 출제 시점에 정해진다

```lua
-- QuestionService.next()
local answer: Zone = if rng:NextInteger(0, 1) == 0 then "A" else "B"
```

`make()` 는 '정답 보기'와 '오답 보기'만 만들고, 둘 중 어느 쪽이 A 바닥에 놓이는지는
**매 출제마다 새로** 정한다. DB 에 존을 박아두면 같은 문제를 두 번 본 사람이 문제를
읽지 않고 정해진 쪽으로 달린다.

### 중복 회피

- 최근 `Config.Question.RecentHistorySize`(10) 개의 **중복 키**는 다시 내지 않는다.
- 같은 **유형**(`source.id`)이 두 라운드 연속으로 나오지 않는다.
- `MaxDrawAttempts`(12) 번 재추첨해도 못 찾으면 **중복을 허용한다.**
  라운드를 멈추는 것보다 같은 문제가 한 번 더 나오는 편이 낫다.

> ### ⚠ 중복 키는 본문이 아니다 — `Draft.key`
> 텍스트 문제는 본문(`"4 + 7 = ?"`)이 곧 문제라서 본문을 키로 써도 된다.
> **이미지 문제는 다르다.** 본문이 항상 `"이 동물은?"` 으로 같아서, 본문으로 판정하면
> 첫 출제 직후부터 **모든 재추첨이 중복으로 걸린다.** 12번을 다 태우고 중복 허용 경로로
> 떨어지므로 회피가 통째로 무력해진다.
>
> 그래서 `Draft.key` 가 있다. 이미지 문제는 `"animal-name:고양이/강아지"` 처럼
> **실제로 무엇이 나왔는지**를 키에 적는다. 비워 두면 `prompt` 로 폴백한다 —
> 즉 텍스트 문제는 아무것도 안 해도 되고, **이미지 문제는 반드시 채워야 한다.**

### 난이도

`Config.getMaxDifficulty(round)` **이하**의 문제 중에서 뽑는다. 이하이므로 후반에도
쉬운 문제가 계속 섞여 나온다 — 난이도가 계단처럼 점프하면 하이퍼캐주얼에서는 이탈로 직결된다.
커브 정밀 조정은 Phase 4 의 몫이다.

## 5. 바닥 스크린 — ★ 여기가 함정 밀집 구역이다 ★

기획서 3장: "A구역과 B구역의 **바닥 자체**가 거대한 디스플레이가 되어 선택지를 출력함."
`ZoneFloorA/B` 에 이미 `BO_AnswerScreen` 태그가 붙어 있고(map-builder.md §5),
`QuestionDisplay` 가 그 파트의 `Top` 면에 `SurfaceGui` 를 붙인다.

### 캔버스 규약 — Studio 실측값이다. 추측하지 마라

40 × 220 파트의 `Top` 면 SurfaceGui(`PixelsPerStud = 8`)를 실제로 측정한 결과:

```
AbsoluteSize = 1760 × 320 px  =  220 × 40 studs

  캔버스 가로(X) = 레인 '길이' 방향 (월드 Z)   ← 긴 쪽이 가로다
  캔버스 세로(Y) = 레인 '폭'  방향 (월드 X)
  캔버스 x = 0   = +Z 끝 (벽 쪽)
  캔버스 x = 1   = -Z 끝 (스폰 쪽)
```

**직관과 다르다.** "바닥을 내려다보니 위쪽이 먼 쪽(+Z)이겠지"라고 추측하면 90° 틀린다.
그래서 글자를 그냥 놓으면 레인을 따라 **옆으로 눕는다.**

### 라벨 회전 `-90` — 이것도 실측값이다

```lua
Config.Theme.Screen.LabelRotation = -90   -- +90 을 넣으면 정확히 180° 뒤집힌 글자가 나온다
```

회전하면 라벨의 가로·세로가 맞바뀐다. 그래서 `MapLayout.answerBand()` 는 **'회전 전' 크기**를
돌려주되, 회전 후에 `가로 = 레인 폭 전체`, `세로 = 원하는 레인 방향 깊이` 가 되도록 미리
뒤집어 계산해 둔다. 배치는 `AnchorPoint (0.5, 0.5)` 라 회전해도 중심이 그대로다.

> **호출부에서 캔버스 스케일 산술을 하지 마라.** 규약이 바뀌면 `MapLayout` 한 곳만
> 고치면 되도록 모아 뒀다. map-builder.md §4 의 "좌표는 MapLayout 에만" 과 같은 규칙이다.

### 왜 선택지를 스폰 바로 앞에 두는가

바닥 글자는 눈높이에서 **거의 눕혀 보인다.** 스폰(Z = -65)에서 바닥을 보는 시선각은 약 8°,
즉 체감 크기가 거리의 제곱에 가깝게 줄어든다. 실측:

| `AnswerBandCenterZ` | 스폰에서 본 체감 크기 | 판정 |
|---|---|---|
| `+10` (레인 중앙) | 화면 세로의 약 2.5% | 읽을 수 없다 |
| `-30` (스폰 바로 앞) | 충분히 읽힌다 | ✔ 채택 |

`AnswerBandDepth`(70)는 글자 높이의 **상한**이다. 실제 크기는 보통 레인 폭(40 studs)에
먼저 걸리므로 여유만 주면 된다. 답이 최대 3자리(예: `162`)라 폭이 항상 먼저 제한한다.

### 발밑 A/B 표기

기획서에 없지만 넣었다 — 라운드 중 옆 레인으로 다이브하면 자기가 어느 구역에 있는지
순간적으로 헷갈리기 때문이다. **단, 선택지를 압도하면 안 된다.** 발밑이라 카메라에
훨씬 가까워서 같은 크기로 두면 선택지보다 크게 보인다. 그래서 깊이 10 studs,
투명도 0.75 로 배경에 녹여 뒀다.

### 선택지가 사진일 때 (`choiceKind = "image"`)

같은 자리에 `ImageLabel`(`ScaleType = Fit`)을 대신 띄운다. 위치·회전은 글자와 완전히
같으므로 코드에는 분기 하나뿐이지만, **에셋 규격이 다르다.** 사진도 8° 로 눌리기 때문이다.

- **정사각형, 단색 배경, 굵은 실루엣.** 사진보다 픽토그램/아이콘에 가깝게.
- **세부 질감·그림자 금지.** 뭉개지면 두 보기가 같아 보이고, 그 라운드는 찍기가 된다.

본문 사진(공중 보드)은 정면으로 보이므로 이 제약이 없다 — **두 용도의 규격은 다르다.**

### 판정 강조 (`reveal`)

`Judge` 단계에서 정답 바닥을 초록, 오답 바닥을 빨강으로 물들인다.
**바닥 파트의 색을 바꾸지 않는다** — SurfaceGui 안의 `Tint` 프레임만 건드린다.
파트 색을 건드리면 손으로 꾸민 재질·색이 라운드마다 덮어써진다.

## 6. 공중 문제 보드 — 본문 사진이 뜨는 유일한 곳

`BO_QuestionBoard` (80 × 32, 중심 `(0, 60, +127)`, 두 레인 중앙 상공). 배치 근거와
기하 제약은 [map-builder.md §5·§7](map-builder.md).

### 왜 HUD 가 아니라 월드인가

기획서 3장의 UI 원칙은 "화면을 가리는 UI 로 시야를 뺏지 않는다" 이고, 그래서 HUD 는
상단 밴드(화면 세로 30%) 안에 갇혀 있다. 그 안의 본문 칸은 **화면 세로의 14%** 밖에 안 된다 —
1080p 에서 약 150px 로, 동물을 알아보라고 하기엔 작다.

원칙을 깨고 HUD 를 키우는 대신 사진을 월드로 내보냈다. 결과적으로 **HUD 는 지시문만,
사진은 경기장 끝 대형 스크린이** 맡는다. 그래서 `QuestionPayload` 에는 `promptImage` 가
아예 없다 — 클라이언트가 알 필요가 없는 정보다.

### 왜 레인 안이 아니라 벽 뒤인가

보드는 벽 높이(40) 위에 있어야 한다. 두 레인의 벽을 합치면 맵 폭 전체를 덮으므로
"벽 사이로 보이겠지"는 성립하지 않는다. 그런데 높이 있는 물체를 가까이 두면 올려다보는
각이 커져 **바닥을 보는 시선과 충돌한다.**

| 보드 Z | 스폰(Z=-65)에서 올려다보는 각 | 판정 |
|---|---|---|
| `0` (레인 중앙) | 약 40° | 바닥 선택지와 시선이 충돌 |
| `+127` (벽 뒤) | 약 16° | ✔ 채택 — 정면을 보면 보드, 시선을 내리면 바닥 |

경기장 끝의 대형 스코어보드와 같은 배치다. 벽 출발선(+114) 바깥이라 벽이 지나가지도 않는다.

### 보드 안의 배치

본문에 사진이 있느냐에 따라 `layoutBoard()` 가 매 라운드 다시 나눈다.

```
사진 없음:  ┌─────────────────────────────┐
            │        4 + 7 = ?            │   지시문이 보드를 다 쓴다
            └─────────────────────────────┘

사진 있음:  ┌──────────┬──────────────────┐
            │ 이 동물은?│       🐱         │   좌 34% 지시문 / 우 63% 사진
            └──────────┴──────────────────┘
```

**위아래가 아니라 좌우로 자른다.** 보드가 가로로 2.5배 길어서, 위아래로 자르면
`ScaleType.Fit` 이 사진의 한 변을 세로에 먼저 걸어 작아진다. 좌우로 나누면 사진이
보드 높이를 그대로 쓴다. 비율은 `Config.Theme.Board.ImageCaptionWidth`.

### 보드가 없으면 사진 문제가 안 나온다

보드 없이 본문이 사진인 문제를 내면 지시문(`"이 동물은?"`)만 뜨고 사진은 어디에도 없는 —
**아무도 풀 수 없는 라운드**가 된다. 그래서 `QuestionService.poolFor()` 가
`QuestionDisplay.hasBoard()` 를 보고 그런 유형을 후보에서 뺀다.

- 서버는 그대로 뜬다. 치명이 아니라 `QuestionDisplay` 의 **경고**다.
- **선택지가 사진인 문제는 계속 나온다** — 그건 바닥이 그리므로 보드와 무관하다.
- 보드를 만들려면 Edit 모드에서 `MapBuilder.addMissing()` (map-builder.md §8).

## 7. HUD

`화면 상단 밴드 하나`가 전부다. 위에서부터 상태 → 문제 본문 → 타이머 → 알림.

- **선택지는 HUD 에 없다.** 바닥이 보여준다. 기획서 3장의 UI 원칙이다.
- **본문 사진도 HUD 에 없다.** 공중 보드가 보여준다 (§6). HUD 가 받는 것은 지시문 텍스트뿐이다.
- **화면 중앙·하단을 비운다.** 하단은 플레이어가 바닥을 보는 영역이다.
- 타이머는 `Config.Theme.Hud.TimerWarnAt`(1.5초) 이하에서 경고색으로 바뀐다.
- 문제 본문은 `Countdown` 과 `WallRush` 동안 계속 떠 있다. 벽이 오는 중에도 옆 레인으로
  다이브할 수 있으므로(round-loop.md §4), `WallRush` 에서 문제를 지우면 마지막 판단
  근거가 사라진다.

`QuestionShown.deadline` 과 `RoundStateChanged.endsAt` 은 **같은 값**이다.
`RoundService.beginTimedState()` 가 계산한 하나를 둘이 나눠 쓴다 — 각자 계산하면
둘이 어긋나 타이머가 튄다.

## 8. 새 문제를 추가하는 법

### 텍스트형 — `QuestionBank.TEXT_SOURCES`

항목 하나를 넣으면 끝이다.

```lua
textSource("double", 2, function(rng)   -- id, 난이도, 생성기
    local n = draw(rng, RANGE.Digit)
    return numbers(`{n} + {n} = ?`, n * 2, nearMiss(rng, n * 2, SPREAD.Near))
end),
```

`id` 는 유일해야 한다(연속 출제 방지에 쓰인다). 난이도는 `Config.getMaxDifficulty(round)`
이하일 때 후보가 된다.

`make` 는 **호출될 때마다 서로 다른 문제**를 만들어야 한다. 항상 같은 값을 돌려주면
중복 회피가 그 문제를 10라운드 동안 통째로 막는다.

두 축이 모두 `"text"` 가 아닌 문제를 손으로 넣고 싶다면 `textSource` 대신 테이블을 그대로 쓴다:

```lua
{ id = "…", promptKind = "text", choiceKind = "image", difficulty = 1, make = … },
```

### 이미지형 — `ImageAssets` 의 `entries` 를 채운다

**`QuestionBank` 는 건드리지 않는다.** 세트에 항목만 넣으면 `{set}-name` / `{set}-photo`
두 종류가 자동으로 등록된다(§3).

```lua
{ id = "animal", prompt = "이 동물은?", difficulty = 1, entries = {
      { name = "고양이", asset = "rbxassetid://0000000000" },
      { name = "강아지", asset = "rbxassetid://0000000000" },
      { name = "코끼리", asset = "rbxassetid://0000000000" },
} },
```

나머지는 **이미 전부 동작한다.**

| 무엇이 | 어디서 |
|---|---|
| 이미지 문제를 섞어 뽑기 | `QuestionService.poolFor()` — `Config.Question.ImageChance`(0.3) |
| 바닥에 사진 그리기 | `QuestionDisplay` — `ImageLabel`, `ScaleType = Fit` |
| 보드에 본문 사진 그리기 | `QuestionDisplay.layoutBoard()` |
| 접속 시 미리 내려받기 | `ImagePreload` — 서버의 `GetImageAssets` |

체크리스트:

1. **선택지용 사진은 §5 의 규격**(정사각 픽토그램)을 지킬 것. 본문용은 자유.
2. **세트 하나에 최소 3~4개.** 2개면 매번 같은 쌍만 나온다.
3. **한 세트 안에서 헷갈리지 않게.** 고양이 ↔ 호랑이는 세트를 나눠라.
4. **`ImageAssets` 를 `Shared` 로 옮기지 말 것.** ID↔이름 대응표가 곧 정답이다 (§2).

## 9. 검증 방법

### 부팅 로그

```
[MapService] 맵 확인 | 80x220 studs | 벽 이동거리 228 studs (1R 4.15s) | 경고 0건
[QuestionDisplay] 바닥 스크린 2개 | 공중 보드 1개
[BrainOverrun] 서버 부팅 완료
[BrainOverrun] 디버그 모드 | 1R 제한시간 5s, 1R 벽속도 55 studs/s | 문제 16종(텍스트 10, 이미지 6)
[BrainOverrun] 이미지 에셋 3세트 7항목 | 공중 보드 있음
```

| 이상한 값 | 뜻 |
|---|---|
| `바닥 스크린 2개` 가 아님 | `BO_AnswerScreen` 태그나 `Zone` 어트리뷰트 누락 → `start()` 가 부팅을 세운다 |
| `공중 보드 0개` | 보드가 없다. `MapBuilder.addMissing()` 실행 (map-builder.md §8) |
| `이미지 0종` + `0항목` | 에셋 미등록. 에러는 아니지만 지금은 7항목이 정상이다 |
| `이미지 0종` + 항목 있음 | 항목이 2개 미만인 세트뿐이다. 세트당 2개 이상 필요 |

클라이언트 콘솔에는 프리로드가 끝났을 때 `[ImagePreload] 문제 이미지 N개 준비 완료` 가
찍힌다. 에셋이 없으면 아무것도 안 찍히는 것이 정상이다.

### 라운드 로그 (서버 콘솔 전용)

```
[Round] R1 출제: 4 + 7 = ? | A=11 B=13 → 정답 A (난이도 1)
[Round] Countdown | R1 | 생존 1
```

정답 구역이 A/B 로 고르게 섞이는지, 난이도가 라운드에 따라 오르는지 확인한다.

### 정답이 새지 않는지 확인 (Client datamodel)

```lua
-- 클라이언트에서 문제 DB 와 에셋 대응표에 접근할 수 없어야 한다
print(game.ReplicatedStorage.Shared:FindFirstChild("QuestionBank"))  -- nil 이어야 정상
print(game.ReplicatedStorage.Shared:FindFirstChild("ImageAssets"))   -- nil 이어야 정상

-- 페이로드에 answer 도 promptImage 도 없어야 한다
game.ReplicatedStorage.Remotes.QuestionShown.OnClientEvent:Connect(function(p)
    for key in p do print(key) end
    -- id, prompt, choiceKind, choices, deadline
    -- answer 나 promptImage 가 보이면 버그
end)

-- 프리로드 목록에 '이름'이 섞이면 안 된다
local ids = game.ReplicatedStorage.Remotes.GetImageAssets:InvokeServer()
print(ids)   -- {"rbxassetid://…", …} 뿐이어야 한다. name 이 보이면 정답이 새고 있다

-- 바닥 파트에 정답 흔적이 없어야 한다
local floor = game:GetService("CollectionService"):GetTagged("BO_AnswerScreen")[1]
print(floor:GetAttributes())   -- Zone, LayoutKey 뿐이어야 한다
```

### 바닥 스크린 방향 확인

Play 후 스폰 지점에서 정면(+Z)을 보면 **두 레인의 선택지가 동시에, 똑바로** 읽혀야 한다.
글자가 90° 누워 있으면 `LabelRotation` 이 0 이 된 것이고, 180° 뒤집혀 있으면 `+90` 이 된 것이다.

같은 시야에 **공중 보드가 정면으로** 보여야 한다. 글자가 좌우로 뒤집혀 보이면 보드가
반대 방향(`Face`)을 보고 있는 것이고, 라운드 시작 때 벽에 가려 안 보이면 보드가 너무
낮은 것이다 (map-builder.md §7-8).

## 10. 불변 조건 (깨면 게임이 망가진다)

1. **`QuestionBank` 와 `ImageAssets` 는 `src/server/` 에 둔다.** `Shared` 로 옮기는 순간
   정답이 공개된다. 특히 `ImageAssets` 는 사진↔이름 대응표라 그 자체가 정답표다.
2. **클라이언트로 나가는 문제는 `payloadOf()` 를 거친 것뿐이다.** `Question` 을 그대로
   `FireAllClients` 에 넘기지 마라.
3. **프리로드 목록에는 이름을 넣지 않는다.** `assetIds()` 가 평탄한 ID 배열을 만드는 이유다.
4. **`reveal()` 은 `Judge` 이후에만 호출한다.** 위로 올리면 정답 강조가 곧 정답 공개다.
5. **정답 구역은 `QuestionService` 가 정한다.** DB 에 존을 박지 마라.
6. **캔버스 스케일 산술은 `MapLayout` 에만.** §5 의 규약은 직관과 다르므로 호출부에서
   다시 계산하면 반드시 틀린다.
7. **선택지와 본문 사진은 HUD 에 넣지 않는다.** 월드가 보여주는 것이 기획의 핵심이다.
8. **이미지 문제의 `Draft.key` 를 비우지 않는다.** 비우면 중복 회피가 무력해진다 (§4).
